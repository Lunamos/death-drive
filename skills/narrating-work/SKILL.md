# Narrating work

## Overview

The user reads a report to judge, quickly, whether the work is true, whether it is interesting, and what should happen next.
Explain each finding as if the listener knew nothing about the project: the plain phenomenon, why it is surprising, and what it
means.

## Reporting a finding

1. **The phenomenon** in one plain sentence, understandable without the project's vocabulary.
2. **Why it matters:** the belief it contradicts, or the problem it solves.
3. **The decisive evidence:**
   - baseline -> result;
   - the control that rules out the obvious alternative;
   - the breadth: how many systems and settings.
4. **The explanation**, if known, and how certain it is. Keep measured facts separate from interpretation.
5. **What it opens:** the next question, and the experiment that would most strengthen or break the claim.
6. **Decisions for the user,** as options with a recommendation.

## Style

- **Plain words.** Name things by what they do. Mention internal codes and file names only when asked.
- **Few numbers.** One or two numbers carry the point, always with their baseline.
- **Short first.** Give details on request.
- **Language.** Write in the user's language.
- **Confidence where earned.** State limits once, where they matter; no defensive hedging.

## Progress

- **During long work,** send a line on what is being done and why.
- **For a problem or a mistake,** say what happened, its effect on the claims, and what was done about it.

## Summarizing a whole project

1. The question.
2. The turning points, and why each one changed the direction.
3. The main claims, each with its strongest evidence.
4. What remains open.
